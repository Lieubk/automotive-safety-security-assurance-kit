Qualification test strategy

PLN-0005 Software qualification test strategy

statusapproved
kindsoftware-qualification-test

Scope

Test object: the complete software of release R1.0 as the last step of the integration strategy builds it (PLN-0004, step application) - WindowPos, AntiPinch, WindowCmd and MotorDrive - with the platform as a double. Tested against: every software requirement SWR-0001 to SWR-0009; all of them are assigned to release R1.0 and have verification_method: test.

Not tested here: the software on the control unit of the door module with the customer's basic software. Timing on the target, the real sensor and bridge driver and the vehicle are tested by the customer in the system qualification test; the delivery names this.

Approach

Test cases are derived from the software requirements and their Verification criteria, never from the design or the code: at least one case per requirement, one step or more per criterion, the values and times of the criterion as expected results. Where a criterion cannot be stimulated in the integrated software, the case says why and names the level that shows it instead.

Stimuli, as a test bench would apply them to the control unit:

  • the Hall signal as a pulse train of given period (open loop, independent of the bridge output);
  • the switch request as the communication stack delivers it, including the invalid value after a reception time-out;
  • a fault of the bridge driver (E_NOT_OK of IFC-0008);
  • for SWR-0006 only: a wrong value of an input of the obstacle detection, put in by the platform double where the integration code passes it on, as a measurement and calibration tool overwrites a signal on the control unit.

Observed: the bridge command (IFC-0008), and as measurement points the window position and speed (IFC-0002), the detection status (IFC-0003) and the movement command in force (the measurement access of MotorDrive). A requirement on a value inside the software is judged at its measurement point.

Known limit of the integrated software: opening and speed come from the same pulses, so a criterion that holds the opening while the speed changes (SWR-0004, criterion 4, at 5.0 mm and 5.5 mm) is shown at a margin here and exactly at unit level (UT-0016).

Regression: after any change of the software under test, all cases run again on the new build of the last integration step. A run always contains every approved case; a case that cannot run is recorded as not-run with its reason.

Criteria

Entry: the last integration step passed on the build to be qualified (PLN-0004 exit criteria), and the build record of that step names the commit to be qualified.

Pass criterion of a case: every expected result holds. Exit: every approved case passed in the latest qualification run, which names the latest build of the last integration step made from the same commit (no COV-18, no COV-38). A failed case gets a problem report and is closed by a correction and a new run, never by changing the case.

Environment and tools

  • Environment software-in-the-loop: a development computer; the software of the last integration step with the platform double of tests/integration/doubles/.
  • tests/qualification/run_tests.py builds that software with the test program tests/qualification/test_qualification.c, runs it and writes the result file; compiler as for the unit tests, warnings treated as errors.
  • Records: tools/record.py test-run --level software-qualification --build <BLD-ID>, BLD-ID being the build record of step application made from the same commit. A test bench of the customer would hand in its JUnit report instead of the result file.

The environment shows the logic of the complete software and its reaction times in cycles of 5 ms and 20 ms. It does not show execution times or the behaviour of the target compiler. None of the tools is qualified.

SQT-0001 Window opening from Hall pulses

statusapproved

Preconditions

Test program tests/qualification/test_qualification.c, built by tests/qualification/run_tests.py from the software of the last integration step (PLN-0004, step application) and the platform double; stimuli and measurement points as PLN-0005 names them. A cycle is 5 ms; every fourth cycle the 20 ms task follows. "Referenced": start, switch request OPEN for 300 ms with the window at the open end stop (no pulses), then NONE for 40 ms. "A movement by n pulses": the switch starts the drive, n pulses follow 3 ms apart from 3 ms after the drive started, and the switch is released so that the drive stops in the cycle of the last pulse. "Pulses at v mm/s": a pulse train with the period that 0.5 mm takes at v mm/s. Positions in counts of 0.5 mm.

Steps

  1. Referenced.
  2. A closing movement by 100 pulses.
  3. An opening movement by 20 pulses.
  4. With the drive stopped, 3 pulses 3 ms apart.
  5. With the drive stopped, a pulse and a second one 399 us after it; then a pulse and a second one 400 us after it.
  6. OPEN with 120 pulses 3 ms apart; NONE; CLOSE with 1000 pulses 3 ms apart.

Expected result

  1. Position 960 (480.0 mm).
  2. Bridge off; position 860 (430.0 mm).
  3. Position 880 (440.0 mm).
  4. Position 883 (441.5 mm).
  5. The first pair changes the position by 1 count, the second pair by 2 counts.
  6. Position 960 after the opening, 0 after the closing; no reversal request.
