Scope

Goal: the software of the power window control with anti-pinch protection for one door, as the customer's system requirements 2.1 and system architecture 1.4 ask (see inputs in project.yaml). The reason: the customer replaces the window lifter of an existing door module and needs anti-pinch protection at ASIL B.

Delivered: the C sources of the developed units, the component and interface descriptions, the unit verification evidence, the integration of the developed components with WindowCmd and MotorDrive (taken over unchanged from the platform release) and its integration and qualification test evidence from the host, the baselines named in milestones and their notices. Not part of it: integration into the door module software, tests on the target, the hardware, calibration on the vehicle - all with the customer.

Approach

Life cycle: one release, R1.0, in four phases - requirements, design, implementation with unit verification and integration, qualification and release. Each phase ends with the baseline its milestone names; from the requirements freeze on, a change goes through a change request.

Estimation: the owner of a work package estimates its effort in person-days with the software lead, from the number and size of the deliverables, and from the actual effort of finished packages of the same kind.

Criteria

A milestone is reached when its baseline is recorded and communicated. The plan is revised when a milestone is at risk by more than one reporting period, when the scope changes, or when a resource is lost.

Environment and tools

The Git repository of the project; the trace engine and record tool of the toolkit; gcc with gcov and the static analysis of the Microsoft C compiler on the host. No target hardware is needed: there is no test on the target in this scope.

Feasibility

Facts: four milestones over 17 weeks; one software developer and the software lead at half time, a software tester for the last five weeks; the work packages add up to 81 person-days, quality assurance included. Assumptions: the customer answers queries within one week; system requirements 2.1 stay stable until the design freeze. Risk: anti-pinch thresholds may need tuning on the vehicle, which is outside this scope. Decision: feasible, on condition that the customer confirms the system requirements by 2026-03-20 - decided by the project lead on 2026-03-04. The example names roles, not people.
