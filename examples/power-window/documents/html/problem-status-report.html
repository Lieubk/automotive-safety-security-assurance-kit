Scope

A problem is every deviation from an approved item that is found after its approval: a failed test case whose cause is not the test itself, a finding of a review on an item that was not the subject of that review, and every report of the customer or of the team of the window lifter platform. Everyone in the project may report one; the customer and the platform team receive the alerts this plan names.

Problems in the customer's basic software and in the door module are reported to the customer and not resolved here. Problems found by the customer on the vehicle reach the project as a report of the customer and are recorded like any other.

Approach

Every problem is a problem-report in records/problems/, moved through the states of the schema:

  1. open - recorded by whoever found it, with what happens, how to reproduce it and where it was found; a provisional severity.
  2. analysed - the Software lead, or the developer the lead names, finds the cause, the origin and the impact (other items, other users of the same component); the Software lead confirms the severity.
  3. in-resolution - the route is chosen: a correction through the authoring skill of the item and a review; a change request once the item is in a baseline that is not internal; for a component of the window lifter platform, a report to the platform team and the corrected release taken over.
  4. resolved - the correction is approved, the change request implemented, or the corrected release integrated.
  5. closed - accepted by the Software lead, with the run in which the exposing test case passes or the review of the correction as evidence.

A problem that is not one, or a duplicate, is rejected with the reason.

Urgent problems (urgent_severities): the Software lead decides within one day on an immediate action - stop of deliveries, a containment in the software, or none with the reason - and it is recorded in the report.

Alerts (alerts): critical problems go to the customer and the Software lead within one day; major problems to the Software lead and, when a component of the platform is affected, to the platform team within two days. The alert is recorded as a communication record about the problem.

Trends: with every project status report, traceability.py problems is read for origin, detection and age; the Software lead writes the reading and the actions as a problem trend report.

Criteria

  • critical: safety relevant, security relevant, or a delivery has to be stopped;
  • major: a software requirement is not met;
  • minor: everything else.

Closure: the exposing test case passed in a final run on a build that contains the correction, or a final review of the corrected item; every change request that resolves the problem is closed.

Environment and tools

Problem reports are items under version control; python tools/traceability.py problems lists them with their age, history <ID> gives the states over the commits. python tools/record.py communication records alerts, problem-trends the trend report.

Description

SWR-0008, criterion 1: after AUTO_CLOSE the movement command is to stay "closing" until the window speed has been 0 mm/s for 200 ms at an opening of 5 mm or less. Observed: the movement command changes to "stopped" between 180 ms and 195 ms after the window speed became 0 mm/s.

To reproduce: the test function of SQT-0008, step 1, on the software of integration step application, built from WindowCmd of platform release 3.2.0. The check "command closing 195 ms after the speed became 0" fails. Environment: software-in-the-loop on the host, as PLN-0005 describes.

Cause and impact

WindowCmd counts the 20 ms cycles at 0 mm/s inside the closed limit and ends the automatic closing when the count reaches 10. The first counted cycle is already the one in which the speed is 0, so the tenth comes 180 ms after it, not 200 ms (WINDOWCMD_END_STOP_CYCLES used with "at least" instead of "more than").

Impact: a comfort function (QM). The window stands at 5 mm or less when it happens; the motor stops 20 ms earlier than required, which the user does not notice and which does not touch the obstacle detection. Every product that uses WindowCmd of platform release 3.2.0 has the same deviation; that is why the platform team was alerted (CMR-0001). Severity major: a software requirement is not met.

Resolution

Reported to the platform team on 2026-06-16 with the failing step. The platform team released WindowCmd 3.2.1 with the comparison corrected; nothing else changed. Release 3.2.1 is taken over unchanged (CMP-0002, tests/integration/integration.yaml), and the integration and the qualification are repeated on it: BLD-0002, RUN-0003 and RUN-0004. No baseline listed CMP-0002 yet, so no change request was needed.
