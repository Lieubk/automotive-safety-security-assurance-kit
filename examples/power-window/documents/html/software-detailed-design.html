Component designs

CDS-0001 Detailed design of WindowPos

statusapproved

Design concept

The component is split where its two execution contexts meet. Everything that happens at interrupt level is in one small unit, HallCapture (UNT-0001): it accepts or rejects an edge and keeps four numbers. Everything that needs a decision - counting direction, range limits, standstill, reference - is in unit WindowPos (UNT-0002), which runs in the 5 ms task and sees the pulse data only as a copy taken at one instant.

Decisions taken here:

  • No hardware access, no generated headers. The units receive time stamps, the current time and the drive direction as arguments. The integration code of the customer (CMP-0006) connects them to the timer and to IFC-0005. Both units run on a development host unchanged.
  • One copy per cycle. UNT-0002 calls HallCapture_GetSnapshot exactly once per step and works on the copy. Position and speed of one cycle come from the same pulse data.
  • Unsigned differences. Pulse counter (16 bit) and time stamps (32 bit) wrap; all differences are taken modulo the width of the type, so a wrap needs no special case. The pulse counter difference is valid for up to 65535 pulses per step, the time difference for up to 2^31 us; larger time differences mean "edge newer than now".
  • Fixed-point only. Position in counts of 0.5 mm, speed in mm/s, one 32 bit division per cycle.
  • The measuring principle itself (pulse period, not pulse count) is decided in ADR-0001.

  • An edge between the reading of the timer by the integration code and the snapshot has a time stamp later than now_us; UNT-0002 treats the time since the last pulse as 0 in this case.
  • The getters are called by other components in the same task or in the 20 ms task. Tasks do not preempt each other, so they never observe a half-updated step.

CDS-0002 Detailed design of AntiPinch

statusapproved

Design concept

One unit, AntiPinch (UNT-0003), built as a state machine with four states that is stepped once per 5 ms cycle. It has no dependency: position, speed and drive direction of the cycle are the three arguments of the step function, the result is read as one record.

Decisions taken here:

  • Speed drop against a reference of its own. The unit compares the speed with a low-pass filtered copy of it. Slow changes - supply voltage, friction along the travel - move the reference along and are not obstacles; a fall faster than the filter can follow is one.
  • Reference held during a drop. While the speed is more than the threshold below the reference, the reference is not updated. An obstacle cannot pull the reference down and hide itself.
  • Two cycles to confirm. One speed value alone never reverses the window.
  • A lower limit of the reference. A drive that never gets going would otherwise give a reference near zero and could not "fall" any more. With the limit of 50 mm/s a window that stays below 30 mm/s is treated as blocked.
  • Fail to "open". Arguments outside their range during closing start a reversal that is limited by time only (SWR-0006). A position that is "not referenced" is a legal value and is treated as inside the protected zone.
  • Own names for interface values. The value ranges of IFC-0002 and IFC-0005 are repeated as constants of this unit, because the delivered components share no header. Comparing them with the interface items is a point of the unit review.
  • Thresholds and times are named constants in the header; release R1.0 has no calibration at run time.

Dynamic behavior

The component is its unit; the state machine with every transition is in UNT-0003. Seen from outside:

  • AntiPinch_Step is called once per 5 ms cycle, after WindowPos_Step and before MotorDrive_Step (VIEW-0004), with the position and speed of this cycle and the drive direction MotorDrive applied in the previous cycle.
  • AntiPinch_GetStatus is called by MotorDrive in the same cycle and by WindowCmd in the 20 ms task. Tasks do not preempt each other; no data is shared with an interrupt, so nothing needs protection.
  • From the first cycle in which the speed is more than 20 mm/s below the reference, the reversal request is set in the next cycle (VIEW-0003).

Purpose

Turns the edges of the Hall sensor signal into three numbers the rest of the component can work with at task level: how many pulses were accepted, when the last one came, and how far apart the last two were. It is the only code of the component that runs at interrupt level and is kept as short as the task allows.

Behavior

Type HallCapture_SnapshotType (copy of the capture data):

MemberTypeMeaning and range
pulse_countuint16accepted edges since initialisation, modulo 65536; 1 count = 0.5 mm of glass travel
rejected_countuint16rejected edges since initialisation, 0 to 65535, stops at 65535
last_edge_usuint32capture time of the last accepted edge; meaningful once pulse_count has changed
period_usuint32interval between the last two accepted edges; 0 = fewer than two edges accepted

Constants:

NameValueMeaning
HALLCAPTURE_MIN_INTERVAL_US400 usshortest interval between two accepted edges; 1250 mm/s, more than six times the fastest window
HALLCAPTURE_REJECTED_MAX65535value at which the rejected counter stops

HallCapture_OnEdge(timestamp_us):

  1. First edge since initialisation: accept it. Store the time stamp and increment the pulse counter. The period stays 0, as there is nothing to measure against.
  2. Any later edge: interval = timestamp_us minus the stored time stamp, as unsigned 32 bit subtraction.
  3. Interval below 400 us: reject. Increment the rejected counter unless it is 65535. The stored time stamp is not changed, so the next edge is measured against the last accepted one.
  4. Otherwise: accept. Period = interval, store the time stamp, increment the pulse counter (65535 is followed by 0).

HallCapture_GetSnapshot copies the four values inside exclusive area HallData. HallCapture_Init sets everything to its initial value.

Error handling

Not detectable here: edges that are never delivered, and a period that is wrong because the timer wrapped a whole number of times during a pause. The user of the period (UNT-0002) does not use the first period after a standstill for that reason.

Dynamic behavior

Two contexts: HallCapture_OnEdge in Isr_HallCapture, HallCapture_GetSnapshot in OsTask_Control_5ms. The interrupt can interrupt the task at any point except inside the exclusive area; the task cannot interrupt the interrupt. The exclusive area is held for four assignments. HallCapture_Init runs in OsTask_Init before the interrupt is enabled. The unit has no states apart from "no edge yet" and "at least one edge".

Design notes

  • The pulse counter wraps on purpose. Its user takes differences modulo 65536, which is correct as long as fewer than 65536 pulses arrive between two snapshots; at 400 pulses per second and one snapshot per 5 ms there are at most 2.
  • The unit does not know the drive direction and does not convert pulses into millimetres; both belong to UNT-0002.

Purpose

Makes a position and a speed out of the pulse data of UNT-0001: counts the pulses in the drive direction, keeps the result inside the travel range, finds the fully open end stop, and converts pulse timing into millimetres per second in a way that shows a slowing window without waiting for its next pulse.

Behavior

Scaling: position in counts of 0.5 mm (1 count = 1 Hall pulse), 0 = fully closed, 960 = fully open; speed in mm/s without sign.

WindowPos_Step(now_us, direction), after the argument check and one snapshot:

  1. New pulses = snapshot pulse counter minus the counter of the last successful step, as unsigned 16 bit subtraction.
  2. Counting direction: if direction is opening or closing, remember it. If it is stopped, keep the remembered one, so that run-out pulses are counted in the direction of the movement that caused them.
  3. Position (only while referenced): closing subtracts the new pulses, not below 0; opening adds them, not above 960.
  4. Speed:
  5. Time since the last pulse = now_us minus the time stamp of the last edge, unsigned 32 bit; a result above 2^31 - 1 means the edge is newer than now_us and is taken as 0.
  6. Pulses since standstill: add the new pulses, stop at 2.
  7. No pulse since standstill: speed 0.
  8. Otherwise, time since the last pulse 50 ms or more: standstill. Speed 0, pulses since standstill back to 0.
  9. Otherwise, fewer than 2 pulses since standstill: speed 0 (the period of the first pulse spans the pause).
  10. Otherwise: effective period = the longer of the snapshot period and the time since the last pulse. Speed = 0 for 50 ms or more, 500 for 1000 us or less, else 500000 / effective period, rounded down.
  11. Reference: count the consecutive steps with direction = opening and speed 0; any other step sets the count to 0. In the step in which the count reaches 40, and in every further such step, the position is set to 960 and marked as referenced.

Speed states of the unit:

stateDiagram-v2

  OnePulse --> Moving: second pulse
  Standing --> Moving: two or more pulses in one step
  OnePulse --> Standing: 50 ms without a pulse
  Moving --> Standing: 50 ms without a pulse

The speed is 0 in Standing and OnePulse and comes from the effective period in Moving.

After a refused step the getters deliver the values of the last successful step. The caller of WindowPos_Step sees the refusal; AntiPinch receives the same invalid direction and reverses a closing movement (SWR-0006).

Dynamic behavior

All functions run at task level: WindowPos_Init in OsTask_Init, WindowPos_Step as first entry of OsTask_Control_5ms, the getters in that task and in OsTask_Command_20ms. Tasks do not preempt each other, so the unit's data needs no protection. The only contact with the interrupt is the call of HallCapture_GetSnapshot, once per step. The step has no loop; its execution time does not depend on the number of pulses.

Design notes

  • Position and speed are updated even while the drive is stopped, because the glass runs on after the bridge is switched off.
  • The reference is taken while the step sees speed 0, which at the start of an opening movement is the case for the first cycles as well; 200 ms is longer than the 60 ms until the first pulse of a starting drive (SYE-0002) by a wide margin.
  • WindowPos_Position is not changed while the position is not referenced; its value then has no meaning and is never delivered.

Purpose

Decides, once per 5 ms cycle, whether the closing window has met an obstacle, and says for how long the window then has to be driven open. It is the whole of component AntiPinch.

Behavior

Scaling: positions in counts of 0.5 mm (0 = fully closed, 960 = fully open, 65535 = not referenced), speeds in mm/s, times in 5 ms cycles (one call of AntiPinch_Step).

Reference speed: stored with 4 fractional bits (AntiPinch_ReferenceQ4, 1 count = 1/16 mm/s). Update per cycle: stored = stored - stored / 16 + speed, with the division rounding down, then limited to at least 800 (50 mm/s). This is a first-order low-pass with a time constant of 5 ms / ln(16/15) = 77.5 ms; at constant speed the reference reaches the speed exactly. The value compared and reported is stored / 16, rounded down.

What one step does, by state, when all arguments are in range:

  • IDLE: motion closing: go to SETTLING, this is closing cycle 1. Otherwise stay.
  • SETTLING: motion not closing: IDLE. Otherwise count the cycle; in cycle 20 set the reference speed to the current speed, at least 50 mm/s, and go to MONITORING. The speed is not compared in this step.
  • MONITORING: motion not closing: IDLE. Otherwise:
  • Drop: speed + 20 < reference. The reference is not updated. If position is above 10 counts (which includes 65535), count the drop cycle; with the second in a row go to REVERSING. If position is 10 or below, set the drop count to 0.
  • No drop: set the drop count to 0 and update the reference.
  • REVERSING: count the cycle. Go to IDLE if position is at most 960 and has reached the target, or if this is cycle 400. motion is not evaluated.

Entering REVERSING fixes the target: detection position + 240, limited to 960; no target (65535) if the position at detection is not referenced or not trustworthy. Entering IDLE clears reference, counters and target.

With an argument out of range the step does not evaluate the state as above; see Error handling.

position = 65535 is not an error. A reversal is never ended by an out-of-range argument.

Dynamic behavior

Both AntiPinch_Step and AntiPinch_GetStatus run at task level and never concurrently (VIEW-0004); the unit shares no data with an interrupt. The states and transitions are given above. Timing follows from the call period of 5 ms: detection starts 100 ms after the drive has started to close, an obstacle is confirmed in the second cycle of a drop, a reversal without reachable target ends after 2 s. The step has no loop.

Design notes

  • The drop condition is written as speed + 20 < reference, so that no subtraction can go below zero.
  • The invalid position value lies above the zone limit on purpose: one comparison covers "inside the protected zone" and "position unknown".
  • The request is derived from the state when the status is read; it is not stored, so state and request cannot disagree.
