PLN-0004 Software integration and integration test strategy

Scope

Integrated here: the components of the power window application (CMP-0001) - WindowPos (CMP-0003) and AntiPinch (CMP-0004), developed in this project, and WindowCmd (CMP-0002) and MotorDrive (CMP-0005), taken over unchanged from the window lifter platform release 3.2.0 as source code (WindowCmd in release 3.2.1, which corrects PRB-0001).

Not integrated here: the basic software of the door module (CMP-0006). The customer integrates the delivered software with it on the control unit. In every step a double stands in for it, including the integration code that calls the application functions in the order of the execution model (VIEW-0004).

Left to the customer's integration on the control unit, and named in the delivery: execution times and processor load against VIEW-0005, the real capture interrupt and its latency, and the configuration of tasks and exclusive areas against VIEW-0004.

Approach

Two steps along the path from the Hall sensor to the bridge (integration_steps):

  1. detection - WindowPos and AntiPinch, built from the source files of their units. Doubles stand in for MotorDrive (it publishes a prepared motor state and records the reversal request and the speed handed to it), for WindowCmd (it does nothing; the command logic only consumes) and for the platform.
  2. application - WindowCmd and MotorDrive added from the platform release. Only the platform is a double. This step is the complete software of the delivery and the test object of the software qualification test (PLN-0005).

Integration tests are derived from the architecture, never from the code:

  • every software interface: its data elements and operations in the normal range, at the limits it states, with the invalid value or time-out it states, and every return value of an operation;
  • the sequences and states the views show across components (VIEW-0003);
  • the order of the entries in the tasks of VIEW-0004, as far as it shows in data passed within one cycle.

Each test case belongs to the first step whose build contains what it needs (step).

Regression: a change of any file a step builds makes that step and every later step stale (COV-36). Both are then built again and every test case of the stale steps is run again; a run always contains all cases of its step. A change of an interface or a view makes its test cases suspect (SUSPECT): they are reviewed against the new version before the next run counts.

Criteria

Entry, per step: the units of the developed components it adds are approved with code, their latest unit test and analysis runs describe the present code (no COV-30), and the previous step passed.

Pass criterion of a test case: every check in it holds. Exit, per step: the build succeeded without warnings, every approved test case of the step passed in a run on the latest build of the step, and the build contains the present code (no COV-36 and no COV-38). A failed case is reported to the Software lead with the run; it is closed by a correction and a new run, never by changing the case or the criteria.

Environment and tools

  • Environment host: a development computer. The platform is a double (tests/integration/doubles/Platform_double.c) whose task bodies follow VIEW-0004; the stand-ins for the platform's headers are those of the unit tests (tests/unit/host/).
  • tests/integration/run_tests.py builds every step from the plan and the items (files of the components taken over and of the doubles in tests/integration/integration.yaml), writes the build manifest, runs the step's test program and writes the result file. Compiler as for the unit tests, warnings treated as errors.
  • Records: tools/record.py build and tools/record.py test-run --level software-integration --build <BLD-ID>, from the manifest and the result file.

The host shows the logic of the integrated software and the data passed between the components. It does not show timing, load or the behaviour of the target compiler. None of the tools is qualified.

Preconditions

Test program of step detection (tests/integration/test_detection.c), built by tests/integration/run_tests.py from the units of WindowPos (CMP-0003) and AntiPinch (CMP-0004), with the doubles of WindowCmd, MotorDrive and the platform. The MotorDrive double publishes the motor state the test sets and records the reversal request and the speed the 5 ms task hands to it. A cycle is one run of OsTask_Control_5ms by the platform double, 5 ms after the previous one, with the capture time set to the time of the cycle; the edges of a cycle reach the capture interrupt before the task runs. "Referenced" means: start, motor state opening, 40 cycles without edges. Positions in counts of 0.5 mm.

Steps

  1. Referenced.
  2. Motor state closing; edges every 3000 us for 60 cycles (100 edges, the last one at the time of the last cycle).
  3. An edge 399 us after the last accepted edge and another one 400 us after it; one cycle.

Expected result

  1. WindowPos_GetPosition returns E_OK and 960 (480.0 mm).
  2. Position 860 (430.0 mm); speed 166 mm/s (0.5 mm in 3000 us, rounded down).
  3. Position 859: the edge 399 us after the accepted one was rejected, the one 400 us after it was counted.

Preconditions

Test program of step application (tests/integration/test_application.c), built by tests/integration/run_tests.py from the units of WindowPos and AntiPinch and the received sources of WindowCmd (CMP-0002) and MotorDrive (CMP-0005), with the platform double. A cycle is one run of OsTask_Control_5ms; after every fourth cycle OsTask_Command_20ms runs, as in VIEW-0004. The bridge command is what the platform double received in the last call of BridgeOutput_Set: direction 0 off, 1 opening, 2 closing, and the duty cycle. Edges every 3333 us throughout, so that no movement is ended as stalled.

Steps

  1. Switch request CLOSE; 8 cycles.
  2. NONE; 8 cycles.
  3. OPEN; 8 cycles.
  4. 7, the value the stack delivers after a reception time-out; 8 cycles.
  5. OPEN; 8 cycles; then 5, a reserved value; 8 cycles.

Expected result

  1. Bridge command closing at 40 % (soft start: 30 % plus 70 % x 3/20 in the fourth cycle of the movement); motor state closing.
  2. Bridge off.
  3. Bridge opening.
  4. Bridge off.
  5. Bridge opening, then off.

SIT-0006 An obstacle reverses the bridge in the cycle it is detected and ends the automatic closing

Preconditions

Test program of step application (tests/integration/test_application.c), built by tests/integration/run_tests.py from the units of WindowPos and AntiPinch and the received sources of WindowCmd (CMP-0002) and MotorDrive (CMP-0005), with the platform double. A cycle is one run of OsTask_Control_5ms; after every fourth cycle OsTask_Command_20ms runs, as in VIEW-0004. The bridge command is what the platform double received in the last call of BridgeOutput_Set: direction 0 off, 1 opening, 2 closing, and the duty cycle.

Steps

  1. Switch request OPEN for 60 cycles, no edges (window at the open end stop).
  2. NONE for 8 cycles; AUTO_CLOSE for 12 cycles, edges every 3333 us from then on; NONE for 188 cycles.
  3. Edges every 3870 us; cycle by cycle, at most 2 cycles, until the reversal request is set.
  4. Edges every 3333 us for 200 cycles; then no edges for 20 cycles.

Expected result

  1. Position 960: referenced while the motor state was opening at 0 mm/s; bridge off: MotorDrive ended the movement after 250 ms at 0 mm/s.
  2. Bridge closing at 100 %; AntiPinch state MONITORING.
  3. The request is set within 2 cycles, and in that same cycle the bridge command is opening at 100 %.
  4. Request clear (ended after 120 mm); bridge off and motor state stopped: the automatic closing was given up and does not resume.
