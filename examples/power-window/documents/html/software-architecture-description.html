VIEW-0001 Static structure of the power window software

statusapproved

Description

The delivered composition PowerWindowApp with its four components, the basic software of the customer next to it, and every interface between them. An arrow points from the provider of data to its user; for the two function-call interfaces towards the basic software it points from caller to callee.

Two things to read from the picture:

  • The path from the Hall sensor to the bridge - WindowPos, AntiPinch, MotorDrive - is ASIL B throughout and takes no input from WindowCmd.
  • WindowCmd (QM) only consumes data and issues the movement command; MotorDrive lets the reversal request of AntiPinch override that command.

Purpose

Groups everything the software supplier delivers for the window control software (SYE-0001), so that the delivery has one boundary towards the basic software of the customer (CMP-0006).

Responsibility

Contains four components: WindowCmd (CMP-0002), WindowPos (CMP-0003), AntiPinch (CMP-0004) and MotorDrive (CMP-0005). WindowPos and AntiPinch are developed in this project; WindowCmd and MotorDrive are reused without change. The composition has no code of its own.

It is delivered as C source without a generated runtime environment. Every component offers an initialisation function, one function per cycle and read functions; inputs from other components are arguments of the cycle function. The customer's integration code calls the functions in the order given in VIEW-0004 and passes the values of the interfaces on. The composition does not contain this integration code, the operating system configuration or any driver.

The ASIL is the highest of its parts. WindowCmd is QM: no component of ASIL B takes any input from it, and the reversal request of AntiPinch overrides its movement command in MotorDrive (SWR-0007).

Dynamic behavior

The composition has no modes of its own. After the initialisation functions have run, the window is stopped, the window opening is not available and no reversal is requested. The states of the window movement are shown in VIEW-0002, the reaction to an obstacle in VIEW-0003, tasks and budgets in VIEW-0004 and VIEW-0005. The budget above is the sum of the four parts; the stack value is the largest of them plus 32 bytes for the calling integration function.

Purpose

Keeps the rules of the comfort functions - which switch request leads to which movement - in one place, apart from everything that has to be developed to ASIL B.

Responsibility

Turns the switch request (IFC-0006) into the movement command for MotorDrive (IFC-0004): manual movement while the switch is held (SWR-0009) and automatic closing after one touch (SWR-0008). It reads the window motion (IFC-0002), the detection status (IFC-0003) and the motor state (IFC-0005) to end a movement at the closed end stop, to give up automatic closing after a reversal, and to refuse automatic closing while the window opening is not available.

It does not detect obstacles, does not command the bridge driver and provides no interface to another component. Nothing it issues can keep the window closing against a reversal request.

Dynamic behavior

One cycle function, WindowCmd_Step, every 20 ms. Internal states: stopped, manual opening, manual closing, automatic closing (VIEW-0002). A switch request that is lost (no frame for 100 ms) or outside 0 to 3 is treated as NONE. After initialisation the state is stopped. Worst-case execution time objective 120 us per cycle.

CMP-0003 WindowPos - window position and speed acquisition

Purpose

Hides how position and speed of the glass are obtained. The other components see a window opening in millimetres and a speed in millimetres per second; a different sensor would change this component only.

Responsibility

  • Processes every edge of the Hall sensor signal in the capture interrupt (IFC-0001): accepts or rejects it by its distance to the previous edge and measures the pulse period (SWR-0001).
  • Counts the accepted pulses into the window opening, in the direction given by the motor state (IFC-0005), and references the opening at the fully open end stop (SWR-0001, SWR-0002).
  • Determines the window speed every 5 ms from the pulse period and from the time since the last pulse, using the capture time base (IFC-0007) (SWR-0003).
  • Provides opening and speed on IFC-0002.

It is a complex driver because it needs the time stamp of every edge at interrupt level, which the standard input path of the basic software does not deliver.

It does not decide what a speed change means, does not store the opening over a reset, and does not access the timer hardware itself.

Dynamic behavior

Two execution contexts share the pulse data: the interrupt writes, the 5 ms task reads a consistent copy inside exclusive area HallData. After initialisation the opening is "not available" and the speed is 0 mm/s. Speed states: standing (0 mm/s) and moving; moving is entered with the second pulse after a standstill and left when no pulse has arrived for 50 ms. Execution time objectives: 10 us per edge, 40 us per 5 ms cycle; with at most 400 edges per second this is 1.2 % of the processor time.

Purpose

Holds the safety function of the product - recognising that the closing glass meets an obstacle and asking for the reversal - in one small component that depends on nothing but its three input values.

Responsibility

  • Supervises every closing movement, manual or automatic, from the motor state (IFC-0005) and the window motion (IFC-0002).
  • Sets the reversal request on IFC-0003 when the window speed falls below the reference speed inside the protected zone (SWR-0004), and when an input is outside its range during closing (SWR-0006).
  • Clears the request after 120 mm of opening travel, at the fully open position or after 2 s (SWR-0005).

It does not command the motor (MotorDrive acts on the request, SWR-0007), does not know why the window closes, and takes no input from WindowCmd.

Dynamic behavior

One cycle function, AntiPinch_Step, every 5 ms, after WindowPos_Step of the same cycle and before MotorDrive_Step, so that a detection reaches the bridge in the cycle in which it is made. States: IDLE, SETTLING (first 100 ms of closing), MONITORING, REVERSING. After initialisation the state is IDLE and the request is clear. Worst-case execution time objective 30 us per cycle.

Purpose

The only component that commands the bridge driver. Because every motor command passes through it, the priority of the reversal over all other commands is decided in one place.

Responsibility

  • Takes the movement command of WindowCmd (IFC-0004) and the reversal request of AntiPinch (IFC-0003) and commands the bridge driver through IFC-0008. While the reversal request is set, the bridge is driven in the opening direction at 100 %, whatever the movement command says (SWR-0007).
  • Raises the duty cycle from 30 % to 100 % within the first 100 ms of a movement started by the movement command.
  • Switches the bridge off when, in a movement asked for by the movement command, the window speed (IFC-0002) has been 0 mm/s for 250 ms, which is the case at both end stops. A reversal is not switched off this way; it ends with the reversal request (SWR-0005).
  • Publishes the direction in which the bridge is actually driven on IFC-0005.

It does not decide when the window moves and does not detect obstacles.

Dynamic behavior

One cycle function, MotorDrive_Step, every 5 ms, last in the task. A change of the reversal request is on the bridge inputs in the same cycle. The direction on IFC-0005 is the one written to the bridge in that cycle. After initialisation the bridge is off. Worst-case execution time objective 60 us per cycle.

Purpose

Present in the architecture because the delivered application cannot run or be described without it: it schedules the application, delivers its inputs and carries out its outputs. No software requirement of this project is allocated to it; its requirements are the customer's.

Responsibility

For the application it provides:

  • the operating system with the tasks and the capture interrupt of VIEW-0004, and the exclusive area HallData used by WindowPos;
  • the capture timer: notification of every Hall edge (IFC-0001) and the current timer value (IFC-0007);
  • the switch request received from the body network, with supervision of its reception (IFC-0006);
  • the output to the bridge driver (IFC-0008);
  • the standard types header Std_Types.h and the integration code that calls the application functions.

It also contains everything else the door module needs (network management, diagnostics, memory services), which the application does not use.

Dynamic behavior

Start-up: the platform initialises itself, runs the initialisation functions of the application once with the capture interrupt disabled, then enables the interrupt and starts the periodic tasks. Tasks do not preempt each other. Shutdown and sleep are handled by the platform; the application has no part in them.

statusapproved
asilB
security_relevantno
kindsender-receiver
provided_byCMP-0003

elements

namedirectiontypeunitminmaxresolutioninitialinvalidperiod_msdescription
positionoutuint16mm04800.565535655355window opening measured from the fully closed end stop; transported as raw value 0..960 in counts of 0.5 mm; initial and invalid are raw values and mean: not referenced since reset
speedoutuint16mm/s0500105speed of the glass without sign; 0 below 10 mm/s; faster pulse trains are reported as 500; has no invalid value

Description

Position and speed of the glass for every component that needs them. Both elements are updated together, once per 5 ms cycle, by WindowPos_Step, and read through WindowPos_GetPosition and WindowPos_GetSpeed.

  • Consumers in the 5 ms task run after the provider and see the values of the same cycle. The consumer in the 20 ms task sees the values of the last completed 5 ms cycle; tasks do not preempt each other, so position and speed always belong together.
  • The position is "not referenced" from reset until the window has rested on the fully open end stop (SWR-0002). WindowPos_GetPosition then returns E_NOT_OK and the invalid value. Each consumer states what it does in this case: AntiPinch treats the whole travel as protected zone, WindowCmd refuses automatic closing.
  • The speed carries no direction. The direction of the movement is the applied direction of IFC-0005.
  • No time-out supervision: provider and consumers run in the same control unit and the values are read by function call.

statusapproved
asilB
security_relevantno
kindsender-receiver
provided_byCMP-0005

elements

namedirectiontypeminmaxinitialperiod_msdescription
applied_directionoutuint80205direction in which the bridge is driven: 0 stopped, 1 opening, 2 closing

Description

The direction MotorDrive has written to the bridge driver in its last cycle. It is the movement command of IFC-0004 unless a reversal request (IFC-0003) or a standstill at an end stop has changed it.

  • WindowPos counts the Hall pulses in this direction (SWR-0001) and references the window opening while it is "opening" (SWR-0002).
  • AntiPinch supervises the movement while it is "closing" (SWR-0004).
  • WindowCmd compares it with its movement command to notice a reversal or a stop at an end stop.

The consumers in the 5 ms task run before the provider and therefore see the direction of the previous cycle; the delay of 5 ms is covered by the run-out of the drive (SWR-0001, Analysis). A value above 2 is outside the specification; WindowPos refuses the cycle, AntiPinch reverses a closing movement (SWR-0006).

Description

The switch request of the body network (SYI-0003) as the communication stack of the basic software hands it to the application. The stack unpacks the signal from the frame and supervises its reception.

IFC-0007 Capture time base

statusapproved
asilB
security_relevantno
kindsender-receiver
provided_byCMP-0006
used_byCMP-0003

elements

namedirectiontypeunitminmaxresolutiondescription
capture_timeoutuint32us042949672951current value of the free-running timer that also stamps the Hall edges of IFC-0001; wraps at 2^32, every 4294.967296 s

Description

The "now" that belongs to the time stamps of the Hall edges. The integration code reads the timer once at the start of each 5 ms cycle and passes the value to WindowPos_Step as argument now_us. WindowPos uses it for one purpose: the time since the last pulse (SWR-0003).

  • The element has no initial and no invalid value; the timer runs from reset.
  • All arithmetic on it is unsigned and modulo 2^32, so the wrap needs no special case.
  • A Hall edge can be captured between the reading of the timer and the call of WindowPos_Step; its time stamp is then later than now_us. WindowPos treats this as "no time has passed since the last pulse".
  • The value must come from the same timer as the time stamps of IFC-0001. A different time base would make the speed wrong without any means of detection in WindowPos.

The tasks and the interrupt in which the delivered functions run.   • OsTask_Init runs once at start-up, activated by the start-up event of the operating system, with Isr_HallCapture still disabled. HallCapture_Init runs before WindowPos_Init.
  • Isr_HallCapture is the capture interrupt of the Hall sensor input (IFC-0001). It occurs at most 400 times per second in steady movement. It is locked only inside exclusive area HallData, for the copy of four variables (objective: at most 5 us).
  • OsTask_Control_5ms carries the path from sensor to bridge. The order of its entries is part of the design: position and speed first, then the detection, then the motor command, so that a detection reaches the bridge in the same cycle (VIEW-0003). The integration code reads the capture time (IFC-0007) once at the start of the task and passes interface values between the entries as arguments.
  • OsTask_Command_20ms runs the comfort logic.

Tasks do not preempt each other; only the interrupt interrupts a task. Data shared between tasks therefore needs no protection, data shared with the interrupt is protected by the exclusive area. The 5 ms task can be delayed by the longest other task (140 us) and by one interrupt (10 us); this jitter of 0.15 ms is inside the 5 ms left over in the budget of the obstacle reaction (SWR-0004, Analysis).

Each budget_us is the sum of the execution time objectives of the components (resource budgets of CMP-0002 to CMP-0005) plus 20 us for the integration code of a periodic task. Processor load at these budgets: 150 us / 5 ms + 140 us / 20 ms + 400 x 10 us / 1 s = 3.0 % + 0.7 % + 0.4 % = 4.1 % (VIEW-0005).

Design decisions

ADR-0001 Measuring the window speed by pulse period or by pulse count

statusapproved
levelsoftware

Context

The obstacle detection needs the window speed every 5 ms and has to see a fall of more than 20 mm/s within one cycle (SWR-0003, SWR-0004). The only sensor is one Hall signal with one pulse per 0.5 mm of travel (SYI-0001). In steady movement that is one pulse every 2.5 ms to 6.25 ms - about one pulse per 5 ms cycle. The basic software can deliver the signal in two ways: as a capture event with a time stamp for every edge, or as a hardware counter that is read from a task. The choice fixes the interface to the basic software, the interrupt load and what WindowPos has to protect.

Evaluation criteria

  1. Speed resolution in the 5 ms cycle between 80 mm/s and 200 mm/s. Needed: clearly finer than the 20 mm/s threshold of SWR-0004. Weight 3.
  2. Delay until a fall in speed is visible to the detection. Needed: one 5 ms cycle, as budgeted in SWR-0004. Weight 3.
  3. Disturbance rejection: can an edge that is not glass travel be kept out of position and speed (SWR-0001)? Weight 2.
  4. Processor load, against the 10 % assigned to the application (VIEW-0005). Weight 1.
  5. Demands on the basic software: number and kind of resources and interfaces the customer has to provide. Weight 1.

Alternatives

A - Pulse period. A capture interrupt per edge stores the time stamp; the speed is 0.5 mm divided by the time between the last two edges, or by the time since the last edge if that is longer.

B - Pulse count. A hardware counter counts the edges without software; the 5 ms task reads it and derives the speed from the pulses counted in a fixed gate time.

CriterionA - pulse periodB - pulse count
1 Speed resolution1 mm/s over the whole range (period known to 1 us, integer division) - fulfilledone pulse per gate time: 100 mm/s for a 5 ms gate, 20 mm/s for 25 ms, 10 mm/s for 50 ms - not fulfilled below a gate of about 100 ms
2 Delaya new period with every pulse, and the time since the last pulse every 5 ms - fulfilledat least the gate time, 25 ms to 100 ms - not fulfilled
3 Disturbance rejectioneach interval is known, an edge closer than 400 us is rejected - fulfilledevery edge is counted as travel; no means in software - not fulfilled
4 Processor loadat most 400 interrupts per second of 10 us: 0.4 % - acceptableone counter read per cycle, below 0.05 % - best
5 Demands on the basic softwarecapture channel with notification (IFC-0001), readable time base (IFC-0007), one exclusive area - acceptableone counter channel - best

Weighted, with 2 points for fulfilled or best, 1 for acceptable and 0 for not fulfilled: A reaches 3x2 + 3x2 + 2x2 + 1x1 + 1x1 = 18 points, B reaches 0 + 0 + 0 + 2 + 2 = 4.

Decision

Alternative A, pulse period. B fails both criteria the obstacle detection depends on: with a gate time short enough for the time budget it cannot resolve the threshold, and with a gate time long enough to resolve it, the detection alone would take longer than the 20 ms the system architecture allows for the whole reaction (SYE-0001).

Decided by the software lead. The example names roles, not people.

Consequences

  • WindowPos gets a part that runs at interrupt level (HallCapture_OnEdge) and data shared between interrupt and task. This data is read only as a consistent copy inside exclusive area HallData; the customer has to configure that area.
  • The interrupt appears in the execution model with its own budget and stack row (VIEW-0004). Its execution time is part of the timing argument of the obstacle reaction and has to be measured on the door module.
  • Time stamps and the "now" of the 5 ms task must come from the same timer; this is stated as a constraint of IFC-0007.
  • The component is a complex driver rather than a sensor component above the standard input path (CMP-0003).
  • Disturbance rejection becomes possible and is required in SWR-0001.
  • Accepted: 0.4 % processor load for the interrupt.
