## Context

The obstacle detection needs the window speed every 5 ms and has to see a fall of more
than 20 mm/s within one cycle (SWR-0003, SWR-0004). The only sensor is one Hall signal
with one pulse per 0.5 mm of travel (SYI-0001). In steady movement that is one pulse
every 2.5 ms to 6.25 ms - about one pulse per 5 ms cycle. The basic software can
deliver the signal in two ways: as a capture event with a time stamp for every edge,
or as a hardware counter that is read from a task. The choice fixes the interface to
the basic software, the interrupt load and what WindowPos has to protect.

## Evaluation criteria

1. **Speed resolution** in the 5 ms cycle between 80 mm/s and 200 mm/s. Needed: clearly
   finer than the 20 mm/s threshold of SWR-0004. Weight 3.
2. **Delay** until a fall in speed is visible to the detection. Needed: one 5 ms
   cycle, as budgeted in SWR-0004. Weight 3.
3. **Disturbance rejection**: can an edge that is not glass travel be kept out of
   position and speed (SWR-0001)? Weight 2.
4. **Processor load**, against the 10 % assigned to the application (VIEW-0005).
   Weight 1.
5. **Demands on the basic software**: number and kind of resources and interfaces the
   customer has to provide. Weight 1.

## Alternatives

**A - Pulse period.** A capture interrupt per edge stores the time stamp; the speed is
0.5 mm divided by the time between the last two edges, or by the time since the last
edge if that is longer.

**B - Pulse count.** A hardware counter counts the edges without software; the 5 ms
task reads it and derives the speed from the pulses counted in a fixed gate time.

| Criterion | A - pulse period | B - pulse count |
|---|---|---|
| 1 Speed resolution | 1 mm/s over the whole range (period known to 1 us, integer division) - fulfilled | one pulse per gate time: 100 mm/s for a 5 ms gate, 20 mm/s for 25 ms, 10 mm/s for 50 ms - not fulfilled below a gate of about 100 ms |
| 2 Delay | a new period with every pulse, and the time since the last pulse every 5 ms - fulfilled | at least the gate time, 25 ms to 100 ms - not fulfilled |
| 3 Disturbance rejection | each interval is known, an edge closer than 400 us is rejected - fulfilled | every edge is counted as travel; no means in software - not fulfilled |
| 4 Processor load | at most 400 interrupts per second of 10 us: 0.4 % - acceptable | one counter read per cycle, below 0.05 % - best |
| 5 Demands on the basic software | capture channel with notification (IFC-0001), readable time base (IFC-0007), one exclusive area - acceptable | one counter channel - best |

Weighted, with 2 points for fulfilled or best, 1 for acceptable and 0 for not
fulfilled: A reaches 3x2 + 3x2 + 2x2 + 1x1 + 1x1 = 18 points, B reaches 0 + 0 + 0 + 2 + 2 = 4.

## Decision

Alternative A, pulse period. B fails both criteria the obstacle detection depends on:
with a gate time short enough for the time budget it cannot resolve the threshold, and
with a gate time long enough to resolve it, the detection alone would take longer than
the 20 ms the system architecture allows for the whole reaction (SYE-0001).

## Consequences

- WindowPos gets a part that runs at interrupt level (`HallCapture_OnEdge`) and data
  shared between interrupt and task. This data is read only as a consistent copy
  inside exclusive area HallData; the customer has to configure that area.
- The interrupt appears in the execution model with its own budget and stack row
  (VIEW-0004). Its execution time is part of the timing argument of the obstacle
  reaction and has to be measured on the door module.
- Time stamps and the "now" of the 5 ms task must come from the same timer; this is
  stated as a constraint of IFC-0007.
- The component is a complex driver rather than a sensor component above the standard
  input path (CMP-0003).
- Disturbance rejection becomes possible and is required in SWR-0001.
- Accepted: 0.4 % processor load for the interrupt.
