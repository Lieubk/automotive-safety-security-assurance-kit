## Scope

Covers the software units that the project develops: every `software-unit` item with
origin `handwritten`. Reused components are verified by the project they come from and
are taken over with their verification evidence; they are not re-verified here.

Not covered: behaviour that depends on the target (interrupt latency, task timing,
memory layout). It is verified after integration, which the customer performs.

Declared limitation of this example: conformance to a coding guideline set is not
checked, because no guideline analyser is available in the example environment. A
project that claims guideline conformance adds that check to the static verification
below and records its deviations.

## Approach

Each unit is verified statically and dynamically, in this order.

1. Build. The unit compiles without a warning at the strictest warning level of the
   compiler in use; warnings are treated as errors.
2. Static analysis. The compiler's defect analysis runs over every unit source. Each
   finding is either removed or justified in the analysis record.
3. Review. The code is compared with the unit design: every designed function exists
   with the designed interface, nothing is implemented that the design does not
   describe, and error handling matches the design.
4. Unit test on the host. Test cases are derived from the unit design, not from the
   code:
   - one or more cases per designed function for its normal behaviour;
   - boundary values of every parameter and every stored value that has a range;
   - every error return and every reaction to an invalid input;
   - every state and transition of a unit that has states;
   - for ASIL A and higher: cases that inject the failure of each called service.
5. Structural coverage. Measured on the host for every unit. Code that the tests do
   not reach is either tested, removed, or justified; coverage is a check on the test
   set, not a goal the tests are written to hit.

Regression: every change to a unit, to a unit it uses, or to its test code repeats
steps 1, 2, 4 and 5 for all test cases of the affected units. Test cases are never
removed or weakened to make a run pass; a wrong test case is corrected through review.

## Criteria

Entry: the unit design is approved, and the unit's test cases are approved.

Pass criterion of a test case: every check in it holds; a test case that does not
report a verdict counts as failed.

Exit, per unit:
- the build is free of warnings;
- the static analysis has no open finding;
- every approved test case of the unit passed in the latest run;
- structural coverage reaches the target for the unit's ASIL given in
  `coverage_targets`, or each gap is justified, reviewed and recorded as a deviation
  with the coverage figure;
- the results are recorded as a test run and a static analysis run that name the
  version tested.

## Environment and tools

- Host computer; no target hardware. Platform headers the units need are replaced by
  stand-ins kept with the tests.
- Test harness: plain C test functions with a small assertion header, one executable
  per unit; `tests/unit/run_tests.py` builds, runs and writes the result file.
- Compilers: any C99 compiler for the tests. Structural coverage needs gcc with gcov
  (`run_tests.py --coverage`).
- Static analysis: `tests/static/run_analysis.py`, using the analyser of the compiler.
- Records are written from the result files by `tools/record.py`, never by hand.

The tools are not qualified. Their results are evidence for the logic of the units
only; a project with tool confidence requirements evaluates each tool before relying
on it.

## Responsibilities

| Activity | Responsible | Approves |
|---|---|---|
| Unit design, code | Software Developer | reviewer who did not write the unit |
| Test cases and test code | Software Developer or Software Tester | reviewer who did not write them |
| Running tests and analysis, recording | Software Developer | - |
| Deciding on coverage deviations | Software Lead | Functional Safety Engineer for ASIL units |
