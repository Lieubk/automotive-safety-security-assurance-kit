## Scope

Test object: the complete software of release R1.0 as the last step of the integration
strategy builds it (PLN-0004, step application) - WindowPos, AntiPinch, WindowCmd and
MotorDrive - with the platform as a double. Tested against: every software requirement
SWR-0001 to SWR-0009; all of them are assigned to release R1.0 and have
`verification_method: test`.

Not tested here: the software on the control unit of the door module with the
customer's basic software. Timing on the target, the real sensor and bridge driver and
the vehicle are tested by the customer in the system qualification test; the delivery
names this.

## Approach

Test cases are derived from the software requirements and their `Verification
criteria`, never from the design or the code: at least one case per requirement, one
step or more per criterion, the values and times of the criterion as expected results.
Where a criterion cannot be stimulated in the integrated software, the case says why and
names the level that shows it instead.

Stimuli, as a test bench would apply them to the control unit:
- the Hall signal as a pulse train of given period (open loop, independent of the bridge
  output);
- the switch request as the communication stack delivers it, including the invalid
  value after a reception time-out;
- a fault of the bridge driver (`E_NOT_OK` of IFC-0008);
- for SWR-0006 only: a wrong value of an input of the obstacle detection, put in by the
  platform double where the integration code passes it on, as a measurement and
  calibration tool overwrites a signal on the control unit.

Observed: the bridge command (IFC-0008), and as measurement points the window position
and speed (IFC-0002), the detection status (IFC-0003) and the movement command in force
(the measurement access of MotorDrive). A requirement on a value inside the software is
judged at its measurement point.

Known limit of the integrated software: opening and speed come from the same pulses, so
a criterion that holds the opening while the speed changes (SWR-0004, criterion 4, at
5.0 mm and 5.5 mm) is shown at a margin here and exactly at unit level (UT-0016).

Regression: after any change of the software under test, all cases run again on the new
build of the last integration step. A run always contains every approved case; a case
that cannot run is recorded as `not-run` with its reason.

## Criteria

Entry: the last integration step passed on the build to be qualified (PLN-0004 exit
criteria), and the build record of that step names the commit to be qualified.

Pass criterion of a case: every expected result holds. Exit: every approved case passed
in the latest qualification run, which names the latest build of the last integration
step made from the same commit (no `COV-18`, no `COV-38`). A failed case gets a problem
report and is closed by a correction and a new run, never by changing the case.

## Environment and tools

- Environment `software-in-the-loop`: a development computer; the software of the last
  integration step with the platform double of `tests/integration/doubles/`.
- `tests/qualification/run_tests.py` builds that software with the test program
  `tests/qualification/test_qualification.c`, runs it and writes the result file;
  compiler as for the unit tests, warnings treated as errors.
- Records: `tools/record.py test-run --level software-qualification --build <BLD-ID>`,
  BLD-ID being the build record of step application made from the same commit. A test
  bench of the customer would hand in its JUnit report instead of the result file.

The environment shows the logic of the complete software and its reaction times in
cycles of 5 ms and 20 ms. It does not show execution times or the behaviour of the
target compiler. None of the tools is qualified.
