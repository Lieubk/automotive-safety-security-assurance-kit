## Scope

Integrated here: the components of the power window application (CMP-0001) - WindowPos
(CMP-0003) and AntiPinch (CMP-0004), developed in this project, and WindowCmd
(CMP-0002) and MotorDrive (CMP-0005), taken over unchanged from the window lifter
platform release 3.2.0 as source code.

Not integrated here: the basic software of the door module (CMP-0006). The customer
integrates the delivered software with it on the control unit. In every step a double
stands in for it, including the integration code that calls the application functions
in the order of the execution model (VIEW-0004).

Left to the customer's integration on the control unit, and named in the delivery:
execution times and processor load against VIEW-0005, the real capture interrupt and
its latency, and the configuration of tasks and exclusive areas against VIEW-0004.

## Approach

Two steps along the path from the Hall sensor to the bridge (`integration_steps`):

1. **detection** - WindowPos and AntiPinch, built from the source files of their units.
   Doubles stand in for MotorDrive (it publishes a prepared motor state and records the
   reversal request and the speed handed to it), for WindowCmd (it does nothing; the
   command logic only consumes) and for the platform.
2. **application** - WindowCmd and MotorDrive added from the platform release. Only the
   platform is a double. This step is the complete software of the delivery and the
   test object of the software qualification test (PLN-0005).

Integration tests are derived from the architecture, never from the code:
- every software interface: its data elements and operations in the normal range, at
  the limits it states, with the invalid value or time-out it states, and every return
  value of an operation;
- the sequences and states the views show across components (VIEW-0003);
- the order of the entries in the tasks of VIEW-0004, as far as it shows in data
  passed within one cycle.

Each test case belongs to the first step whose build contains what it needs (`step`).

Regression: a change of any file a step builds makes that step and every later step
stale (`COV-36`). Both are then built again and every test case of the stale steps is
run again; a run always contains all cases of its step. A change of an interface or a
view makes its test cases suspect (`SUSPECT`): they are reviewed against the new version
before the next run counts.

## Criteria

Entry, per step: the units of the developed components it adds are approved with code,
their latest unit test and analysis runs describe the present code (no `COV-30`), and
the previous step passed.

Pass criterion of a test case: every check in it holds. Exit, per step: the build
succeeded without warnings, every approved test case of the step passed in a run on the
latest build of the step, and the build contains the present code (no `COV-36` and no
`COV-38`). A failed case is reported to the Software lead with the run; it is closed by a
correction and a new run, never by changing the case or the criteria.

## Environment and tools

- Environment `host`: a development computer. The platform is a double
  (`tests/integration/doubles/Platform_double.c`) whose task bodies follow VIEW-0004;
  the stand-ins for the platform's headers are those of the unit tests
  (`tests/unit/host/`).
- `tests/integration/run_tests.py` builds every step from the plan and the items
  (files of the components taken over and of the doubles in
  `tests/integration/integration.yaml`), writes the build manifest, runs the step's
  test program and writes the result file. Compiler as for the unit tests, warnings
  treated as errors.
- Records: `tools/record.py build` and `tools/record.py test-run --level
  software-integration --build <BLD-ID>`, from the manifest and the result file.

The host shows the logic of the integrated software and the data passed between the
components. It does not show timing, load or the behaviour of the target compiler. None
of the tools is qualified.
