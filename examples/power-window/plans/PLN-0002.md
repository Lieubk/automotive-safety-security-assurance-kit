## Scope

Everything the project produces or relies on to reproduce a delivery:

| Configuration items | Where |
|---|---|
| Plans, requirements, architecture, design, test cases | item files under `plans/`, `spec/`, `verification/` |
| Evidence: reviews, test runs, analysis runs, baselines, communication | item files under `records/`, `verification/runs/`, with tool output under `verification/evidence/` |
| Source code and test code | `src/`, `tests/` |
| Build and test scripts, project configuration | `tests/**/*.py`, `project.yaml` |
| Imported inputs | item files marked `imported`, unchanged from what was received |

Not under this plan: build output (`build/`), which is reproducible from the above.

## Approach

Identification. Every item has an ID that is never reused and is the name of its
file. A version of an item is identified by its content hash; a version of the whole
is identified by a commit.

Version control. One Git repository holds all configuration items. History on the
main branch is never rewritten.

Branches.
- `main` always holds a state in which the trace check reports no error.
- Work happens on a short-lived branch per task or change request, named after it.
- A branch is merged through a reviewed merge request; the reviewer is not the author.

Change control.
- Items that are not yet in a baseline change freely on a branch; an approved item
  that changes loses its approval until it is reviewed again.
- An item inside a baseline changes only through an approved change request that
  names it. The change request lists every affected item before work starts.
- Imported inputs are never edited. A problem with an input is sent to its source as
  a query; a new version from the source is imported as a new version.

Baselines. A baseline is a tag on `main` plus a baseline record listing every item
with its content hash and status.

| Purpose | When | Tag |
|---|---|---|
| working | any time, for internal reference | `work-<date>` |
| requirements freeze | software requirements approved | `req-<n>` |
| design freeze | architecture and detailed design approved | `design-<n>` |
| release candidate | unit verification complete for the release content | `rc-<release>-<n>` |
| delivery | handed to the customer | `rel-<release>` |

Status reporting. `python tools/traceability.py status` and `check` give the status of
all items at any commit; the output for a baseline is attached to its communication
record.

## Criteria

A baseline other than `working` is created only when:
- the trace check reports no error at the commit to be tagged;
- every item in the baseline is approved, and its approval covers the listed hash;
- no change request that affects an item of the baseline is still open, unless the
  baseline record names it as a known open point.

Baseline audit: before a delivery baseline, the record is regenerated at the tag and
compared with the stored record; any difference stops the delivery.

A baseline other than `working` is communicated to the parties named in its
communication record.

## Environment and tools

- Git, with the repository hosted where the team's access rights and backups are
  managed; a clone is a full backup of history.
- `tools/traceability.py` for status, impact and baseline content; `tools/record.py`
  for records.
- Retention: delivery baselines and everything they reference are kept for the
  period the customer contract requires.

## Responsibilities

| Activity | Responsible |
|---|---|
| Keeping this plan and the branch rules | Configuration Manager |
| Creating baselines, baseline audit | Configuration Manager |
| Deciding on change requests | Change Control Board |
| Following the rules in daily work | everyone who commits |
