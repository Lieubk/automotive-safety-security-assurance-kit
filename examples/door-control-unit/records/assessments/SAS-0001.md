## Summary

Rehearsal of SYS.2 and SYS.3 at level 1 by A. Assessor (rates) and B. Second, with E. Engineer and V. Verifier interviewed. The result is a self-assessment of the team's own work; it is not an assessment.

Strengths: every system requirement is derived from an accepted stakeholder requirement and has measurable verification criteria that the qualification cases use; the allocation of every requirement to an element or interface is stated on the architecture side and the review records name what each item was compared with.

Weaknesses: the effect of the requirements on the OEM's neighbours (SYS.2.BP4) is thin because the OEM's message matrix and diagnostic specification were not delivered and no query asked for them; the communication of requirements and architecture (SYS.2.BP8, SYS.3.BP8) names only the OEM contact; the architecture has one decision and one sequence view.

Proposed actions: write queries to the OEM for the message matrix and the diagnostic specification and follow them in the next release; record the communication of the baseline to the hardware department and the bench team; add a state view for the operating modes in B2; apply an independent review pass to the architecture in B2.
