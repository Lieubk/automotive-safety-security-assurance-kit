## Scope

Under configuration management is everything the project produces and everything needed to reproduce a release:

| Configuration items | Where |
|---|---|
| Plans, requirements, architecture, test cases | item files under `plans/`, `spec/`, `verification/` |
| Evidence: reviews, builds, test runs, baselines, communication, suppliers, risks, problems | item files under `records/`, `verification/builds/` and `verification/runs/`, tool output under `verification/evidence/` |
| Imported inputs | item files marked `imported`, unchanged from what was received, and the OEM's document under `inputs/` |
| Bench reports and manifests | files under `inputs/bench/`, as the bench team handed them over |

Not under this plan: build output (`build/`, including the generated documents), because it can be generated from the items. The software element "power window software" is configured by our software department; this project holds its version in the manifests of the system builds. The bench setups and simulations are the test department's and are named in the manifests.

This plan is revised when the repository or a tool changes, when the process scope in `project.yaml` changes and when a second release line is opened.

## Approach

Identification. Every item has an ID that is never reused and is the name of its file. A version of an item is its content hash, a version of the whole is a commit, a released state is a tag. The product has no variants.

Version control. One Git repository holds all configuration items; history on the main branch is not rewritten. Work happens on the main branch of the repository, because the project has two engineers; the configuration manager looks at every commit that changes an approved item.

Change control. Items that are in no baseline change freely; an approved item that changes loses its approval until it is reviewed again. An item inside a baseline other than `working` changes only through an approved change request that names it; the project does not have a change request management plan, because change request management is not in its scope, so a change of a baselined item is agreed with the OEM contact first and recorded in a communication record. Imported inputs are never edited: a problem goes to the source as a query, and a new version is registered as a new version.

Baselines. A baseline is a tag on the main branch plus a baseline record that lists the approved items with content hash and status.

| Purpose | When | Tag |
|---|---|---|
| working | at any time, for internal reference; lists every item in its present state and protects nothing | `work-<date>` |
| release candidate | integration and qualification have passed on the release content; the release is built from it | `dcu-f-<release>-rc`, for example `dcu-f-b1-rc` |

`working` is the only internal purpose (`trace.internal_baselines` in `project.yaml`).

Status reporting. `traceability.py status` and `check` give the status of all items at any commit. The configuration manager passes both outputs to the project lead with every baseline and in every monthly status report.

## Criteria

A baseline other than `working` is created only when the trace check reports no error at the commit to be tagged, every item of the release content is approved, and no change request that affects a listed item is open.

Baseline audit. Before a release, `traceability.py audit <baseline>` is run at the tagged commit: every listed item with its hash and state, and no approved item unlisted. A difference stops the release. The configuration manager keeps the output with the release documents.

Communication. A baseline other than `working` is made known to the OEM contact and to the project lead; who was informed is recorded in a communication record that names the baseline.

## Environment and tools

Git, with the repository on the team's server; only the configuration manager sets tags. `tools/traceability.py` for status, impact, hashes and the audit; `tools/record.py` for baseline and communication records. Backup: the server is backed up daily by its operator.

## Responsibilities

| Activity | Performs | Checks or approves |
|---|---|---|
| Keeping this plan | configuration manager | project lead |
| Creating baselines, setting tags, baseline audit | configuration manager | project lead |
| Following the rules in daily work | everyone who commits | configuration manager, by sampling |
